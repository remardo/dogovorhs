# Аудит DogovorHS — 1 октября 2026

Этот документ фиксирует исходное состояние до исправлений. Текущие результаты и проверка оригиналов: [IMPLEMENTATION_RESULTS.md](IMPLEMENTATION_RESULTS.md). Защита доступа исключена из текущего этапа по прямому указанию пользователя.

## Вывод

Проект можно развивать на существующих React/Vite/Convex. Переписывание стека не требуется. Основная проблема — незавершённая модель учёта и жизненный цикл документов, а не выбор технологий.

Сейчас система хранит реальные счета и расходы по юридическим лицам, но ещё не обеспечивает надёжный ответ на оба главных вопроса: «кто сколько потратил за период» и «кто отвечает за конкретный договор/номер». Истории назначения SIM нет, ответственного за договор нет, связь SIM → договор заменена предположением по компании и оператору.

Первый приоритет — закрыть доступ к данным и защитить учёт от повторного импорта, ошибочного сопоставления и удаления. После этого исправить периоды и навигацию.

## P0 — доступ к реальным данным

### 1. Рабочий API доступен анонимно

**Подтверждено live.** Новый `ConvexHttpClient` без `setAuth` успешно вызвал `dashboard:getSummary`, `invoices:list`, `expenses:list`, `employees:list`, `simCards:list`. `invoices:list` возвращает в том числе URL исходных файлов.

Источник: `convex/_lib/flags.ts:1`, `convex/_lib/auth.ts:15`, `convex/invoices.ts:5`, `convex/billingImports.ts:14`.

Защита включается только при `REQUIRE_AUTH === "true"`; при отсутствии или другом значении доступ разрешён. Публичные mutations используют тот же условный guard. Возможность изменения/удаления без входа следует из кода, но разрушительными запросами в production не проверялась.

**Решение:** полноценный вход и серверная проверка разрешённых пользователей/ролей; обязательная защита чтения, записи и загрузки. Просто включить флаг недостаточно: в приложении нет готового login-flow, настройки профиля являются макетом, а сервер проверяет только наличие identity. Конфигурацию провайдера авторизации в production отдельно не проверял.

**Приёмка:** без сессии недоступны данные и загрузка; читатель не может менять записи; неразрешённый пользователь с валидной identity также получает отказ. Сид сделать internal-функцией или отдельной административной операцией: `convex/seed.ts:3` сейчас не вызывает auth-guard.

## P1 — достоверность учёта

### 2. Повторный импорт детализации повторно создаёт расходы

**По коду.** `billingImports.applyParsed` проверяет существование импорта, но не запрещает повторное применение `status: applied`. Каждый вызов вставляет расходы заново. `updatePreviewSummary` может вернуть статус применённого импорта в `preview`. Загрузка того же файла с новым importId также не распознаётся как повтор.

Источник: `convex/billingImports.ts:87`, `convex/billingImports.ts:124`, `convex/billingImports.ts:448`.

**Решение:** неизменяемое состояние применённого импорта, идемпотентность в mutation, fingerprint документа и понятная операция замены/отмены. Проверить повтор одного importId, повтор файла под другим именем и одновременные вызовы. UI-блокировки кнопки недостаточно.

### 3. Счёт сопоставляется с произвольным расходом того же договора и месяца

**По коду.** `invoices.update` ищет первую строку по companyId + month + строке contractNumber. Не сравнивает номер счёта, сумму, источник, тип услуги. При нескольких счетах или строках детализации может привязать документ к одной неподходящей строке.

Источник: `convex/invoices.ts:142`, `convex/invoices.ts:149`, `convex/invoiceActions.ts:108`.

В `invoiceActions.apply` для услуги, отличной от «Мобильная связь», найденный расход затем перезаписывается суммами счёта. Для мобильной услуги уже существующий расход остаётся с прежними суммами. Оба поведения не обеспечивают сверку документов.

**Решение:** привязка через устойчивые идентификаторы и документный ключ; при конфликте — явная сверка. Нельзя считать два счета одним расходом только из-за общего договора/месяца.

### 4. Счета и детализации независимо увеличивают одни расходы

**По коду.** PDF-счёт создаёт общий расход, импорт детализации вставляет построчные расходы в ту же таблицу. Сверки между путями нет. Если загрузить оба документа за одну услугу и период, сумма может быть учтена дважды.

Источник: `convex/invoices.ts:153`, `convex/billingImports.ts:425`.

**Решение:** счёт задаёт начисление, детализация распределяет это начисление по номерам/сотрудникам. Общая сумма и её распределение не должны складываться. Ручной расход — отдельный источник с явным основанием.

### 5. Применение PDF-счёта не атомарно и не идемпотентно

**По коду.** Action последовательно создаёт счёт, привязывает/создаёт расход и при необходимости меняет его тип. Это отдельные `runMutation`. Ошибка после первого шага оставляет частичный результат; повтор создаёт ещё один документ. На текущем наборе дублей по проверенному ключу нет.

Источник: `convex/invoiceActions.ts:101`, `convex/invoiceActions.ts:108`, `convex/invoiceActions.ts:118`.

**Решение:** извлечение/разбор оставить action, запись счёта и начисления выполнять одной mutation с проверкой повторов. Ключ должен учитывать оператора, юридическое лицо и идентичность документа.

### 6. Перепривязка и удаление нарушают связи учёта

**По коду.** Смена `contractId` счёта не синхронизирует уже существующий expenseId; contractNumber также не выводится автоматически из выбранного договора. Удаление счёта удаляет файл и invoice, но оставляет расход с `hasDocument: true`. Удаление расхода не очищает invoice.expenseId. Удаление договора вообще не проверяет счета.

Источник: `convex/invoices.ts:111`, `convex/invoices.ts:173`, `convex/expenses.ts:84`, `convex/contracts.ts:172`.

**Решение:** серверные операции перепривязки/аннулирования с единым правилом для начисления и документа; архивирование используемых договоров; запрет опасного удаления либо согласованное аннулирование. Текущие связанные записи не удалять массово.

### 7. Дашборд показывает общую сумму как расходы за один месяц

**Подтверждено live и по коду.** На главной: 374 882,53 ₽ «за Октябрь 2026». По API расходы октября — 40 396,47 ₽. Полная сумма относится к пяти месяцам. Карточки компаний при этом показывают именно октябрьские суммы.

Источник: `src/pages/Index.tsx:28`, `src/pages/Index.tsx:42`, `src/pages/Index.tsx:48`, `convex/dashboard.ts:24`, `convex/dashboard.ts:84`.

Причины: стартовый диапазон инициализируется до прихода данных; сумма складывается по всем доступным месяцам, а подпись берётся от первого. Даты фильтра — createdAt загруженных записей, а не период услуги. Пустой результат фильтра возвращает все расходы. Компании и круговая диаграмма не используют выбранный диапазон. Месяцы упорядочены по времени загрузки: октябрь, декабрь, август, сентябрь, июль.

**Решение:** единый фильтр по периоду услуги с ключом `YYYY-MM`, календарная сортировка, согласованные суммы во всех блоках. Для пустого периода — 0 и пустое состояние. Сейчас календарь дневного диапазона не соответствует фактической месячной агрегации; достаточно селектора месяца/диапазона месяцев.

Дополнительно сервер берёт максимум 5000 последних расходов по умолчанию: после роста данных итог может стать неполным без предупреждения (`convex/dashboard.ts:18`). Итоги должны считаться по выбранному периоду, а не по произвольной выборке последних записей.

### 8. Показатели дашборда частично фиктивные

**Подтверждено UI и кодом.** Проценты +2,3%, +3,2%, +1,5% записаны константами. «Активных договоров/SIM» показывает количество всех записей независимо от статуса. «Сотрудников с SIM» зависит от ручного simCount, а не фактических назначений.

Источник: `src/pages/Index.tsx:115`, `convex/dashboard.ts:94`.

**Решение:** удалить проценты до появления корректного расчёта; считать статусы и назначения по реальным данным.

### 9. Нет надёжной модели «договор → SIM → ответственный → расходы»

**По схеме и коду.** В SIM отсутствует contractId. Карточка договора показывает все SIM с той же companyId и operatorId, поэтому при двух договорах одного оператора будут показаны одни и те же номера. Ответственный за договор, адрес подключения интернета и история выдачи SIM отсутствуют. Расход хранит номер SIM и договора строками.

Источник: `convex/schema.ts:51`, `convex/schema.ts:67`, `convex/schema.ts:86`, `src/pages/Contracts.tsx:145`.

**Решение:** явный contractId у номера/подключения и начисления, ответственный за договор, место оказания услуги для интернета. Для назначений нужны даты начала/окончания; расходы должны относиться к ответственному в периоде услуги. Перевыдача SIM не должна переписывать смысл прошлых месяцев.

### 10. Назначения SIM и счётчики расходятся

**По коду.** simCount сотрудника и договора вводится руками. Изменение employeeId SIM не обновляет счётчик. Сервер проверяет наличие сотрудника/тарифа, но не компанию сотрудника, статус увольнения, соответствие оператора тарифу или maxSim. Обновление сотрудника позволяет перевести его в другую компанию с назначенными SIM.

Источник: `convex/employees.ts:30`, `convex/simCards.ts:58`, `src/pages/Employees.tsx:467`, `src/pages/Employees.tsx:504`.

Отвязка передаёт `employeeId: undefined`; нормализация делает поле undefined, которое не даёт надёжного явного намерения очистить связь в JSON-аргументах. У mutation нет отдельной команды clear/unassign. Аналогичная проблема касается снятия тарифа.

**Решение:** вычислять счётчики из назначений; серверная проверка лимита и совместимости; явная операция назначения/снятия с null или отдельным аргументом действия. Проверить фактическое снятие связи интеграционным тестом после исправления.

### 11. В справочниках сохранены демонстрационные реквизиты

**Подтверждено live и сравнением с seed.** У трёх исходных компаний ИНН/КПП совпадают с шаблонными значениями в `convex/seed.ts`. У исходных операторов остались демонстрационные менеджеры/телефоны. Эти записи уже используются настоящими договорами.

Источник: `convex/seed.ts:12`, `src/pages/Companies.tsx`, `convex/invoiceActions.ts:43`.

**Риск:** автоматический подбор компании по ИНН не будет работать правильно; справочник выглядит достоверным, хотя часть данных — пример.

**Решение:** сверить реквизиты с реальными документами и обновить существующие записи с сохранением ID. Не удалять компании вместе со связями. Неизвестные реквизиты пометить как требующие проверки.

### 12. Типы услуг договоров и расходов уже расходятся

**Подтверждено live.** В расходах: 21 «Интернет» и 14 «Мобильная связь»; в договорах: 1 «Интернет» и 34 «Мобильная связь». Требуется сверка, нельзя автоматически считать всю вторую группу мобильной.

Источник: `convex/contracts.ts:21`, `convex/invoices.ts:158`, `src/pages/Invoices.tsx:92`, `convex/billingImports.ts:428`.

При импорте детализации поле expense.type получает название тарифа вместо категории услуги. В итоге один график смешивает категории, тарифы и «НДС».

**Решение:** отдельная стабильная категория услуги, tariffId отдельно; выбор типа по договору с возможностью подтверждения. Исторические данные сверять с источниками.

## P1/P2 — обработка файлов и клиентский код

### 13. Настоящий XLS не поддерживается, хотя UI его предлагает

**Воспроизведено локально на файле проекта.** Сигнатура XLS: `d0cf11e0a1b11ae1`. Существующий `parseRows` вызывает `workbook.xlsx.load` и падает: `Can't find end of central directory: is this a zip file?`.

Источник: `convex/_lib/billingImportParser.ts:133`, `src/components/expenses/BillingImportDialog.tsx:333`.

**Решение:** либо честно принимать XLSX/поддерживаемый CSV с указанием конвертации XLS, либо добавить поддержку старого формата по реальной потребности. PDF-путь детализации также отмечен как сломанный в инфраструктурной документации; в UI импорта PDF сейчас не предлагается. Production-PDF экшен отдельно не запускался.

### 14. Распознанные PDF нельзя полноценно проверить и исправить до применения

**По коду.** Сумма, НДС, номер счёта и период только отображаются. «Применить» доступно и при предупреждении «не извлечены суммы». kind всегда передаётся как `invoice`, поэтому загруженная через этот UI детализация может стать счётом. При ручном выборе другого договора меняется только contractId, но не исходные companyId и contractNumber.

Источник: `src/pages/Invoices.tsx:114`, `src/pages/Invoices.tsx:190`, `src/pages/Invoices.tsx:248`, `convex/invoices.ts:77`.

**Решение:** редактируемые поля предпросмотра, явный вид документа, обязательная серверная проверка согласованности договора/компании/номера/периода/сумм. Не применять нераспознанные суммы без исправления или явного подтверждения корректного нулевого счёта.

При пакетной загрузке один сбой теряет весь накопленный `next` в UI, хотя предыдущие файлы уже загружены в storage. Повтор загружает их снова. Нужны отдельные результаты файлов и очистка отменённых загрузок.

### 15. Денежная валидация и правила НДС не согласованы

**По коду.** `v.number()` проверяет тип, но не бизнес-правила: сверку amount + vat с total, допустимый период, корректность связей. В парсере PDF-счетов есть расчётный fallback 22%, в распределении/парсере детализации — константа 20%. Это разные правила внутри одного приложения, а не подтверждённая ошибка каждого текущего документа.

Источник: `convex/expenses.ts:56`, `convex/invoices.ts:77`, `convex/_lib/vatDistribution.ts:9`, `convex/_lib/invoiceParser.ts`, `convex/_lib/billingImportPdfMegafon.ts:9`.

**Решение:** брать ставку и суммы из документа; расчётное восстановление помечать и подтверждать. Хранить деньги в целых копейках либо централизованно округлять денежные операции; допустимость отрицательных корректировок задавать явно. В текущих данных существенных арифметических расхождений не найдено.

### 16. Ошибки записи скрываются, после них UI сообщает об успехе

**По коду.** `mutateAndRefresh` ловит исключение и не пробрасывает его вызывающему коду. Формы после `await` показывают «добавлен/обновлён», закрываются и могут сбросить введённые данные. Некоторые удаления даже не ожидают результат.

Источник: `src/lib/backend/index.ts:332`, `src/pages/Contracts.tsx:115`, `src/pages/Invoices.tsx:361`, `src/pages/Expenses.tsx:553`.

**Решение:** mutation возвращает достоверный результат или бросает исключение; успех только после подтверждённой записи, форма остаётся открытой при ошибке. Отличать запрет удаления, конфликт, валидацию и недоступность сети.

### 17. Самодельный слой запросов нестабилен и дублирует Convex

**По коду; live-счётчик запросов не измерялся.** Каждый вызов хука передаёт новую функцию load, а useEffect/useCallback зависят от её identity. Некоторые empty-массивы также создаются заново. Обновления состояния повторно запускают эффекты и пересоздают polling. Layout независимо загружает договоры, SIM и сотрудников на каждой странице.

Источник: `src/lib/backend/index.ts:258`, `src/lib/backend/index.ts:327`, `src/lib/backend/index.ts:377`, `src/components/layout/MainLayout.tsx:26`.

**Решение:** использовать штатные реактивные hooks Convex с одним provider и согласованным состоянием загрузки/ошибки. Переход на другой state manager или собственный универсальный query framework не нужен.

При ошибке чтения данные заменяются пустыми; страницы в основном игнорируют error/isLoading, а health проверяет только ping. Поэтому «нет записей», «идёт загрузка» и «доступ запрещён» визуально не различены.

## UI: навигация, повторения и незавершённые действия

### 18. Кликабельность неоднородна

**Договоры:** live-нажатие на номер открыло карточку. Строки SIM и расходов также кликабельны по коду. Значит, проблема «только через три точки» уже решена частично.

**Сотрудники:** просмотр только через меню, строка не кликабельна (`src/pages/Employees.tsx:332`). **Компании:** live-команда «Просмотр» закрыла меню, но не открыла карточку; у «Просмотр» и «Редактировать» нет обработчиков (`src/pages/Companies.tsx:161`). Аналогичные пустые команды есть у операторов и тарифов (`src/pages/Operators.tsx:181`, `src/pages/Tariffs.tsx:386`).

**Решение:** название/номер — настоящая ссылка на карточку; строка может дополнительно открывать её мышью. «…» оставить для вторичных действий. Ссылка должна работать с клавиатуры и позволять открыть новую вкладку.

### 19. Карточки повторяют таблицы и не раскрывают связанный учёт

**Подтверждено для договора.** Карточка повторяет номер, название, компанию, оператора, статус и абонплату; затем показывает SIM по неточной связи. Нет счетов, начислений по месяцам, ответственного и адреса подключения. Компания на главной почти повторяет карточку справочника, но не ведёт к её расходам. Последние договоры на главной также не дают полноценного перехода в карточку.

**Решение по структуре:**

| Экран | Основной смысл | Что убрать/сократить |
|---|---|---|
| Дашборд | Период, расходы, динамика, несопоставленные/проблемные документы | Повтор полного списка компаний и пассивные последние договоры |
| Договоры | Реестр договоров и условий | Ручные счётчики SIM |
| Карточка договора | Условия, компания, ответственный, подключения, счета, начисления | Повтор всех колонок без связанных данных |
| Сотрудники | Ответственный и расходы за период, назначенные номера | Ручной ввод «сколько SIM» |
| SIM/подключения | Номер/адрес, договор, текущий ответственный, тариф, расход за период | Начисления за всё время без указания периода |
| Счета | Исходный документ, распознавание, привязка, сверка с детализацией | Отдельный непрозрачный путь создания тех же расходов |
| Расходы | Аналитический срез начислений по периоду и получателю | Неидентифицируемые строки «-» вместо услуги/договора |
| Компании/операторы/тарифы | Реквизиты и условия, переходы к связанным записям | Повтор крупных статистических карточек без переходов |

Счета и расходы нужны оба: первый экран — документы, второй — аналитика. Их не нужно механически объединять; нужно связать и использовать один источник начислений. Повтор общей суммы полезен только при одинаковых фильтрах и ясном смысле.

### 20. Список расходов плохо идентифицирует строки

**Подтверждено live.** В большинстве строк колонка «SIM/услуга» содержит «-»: у текущих расходов нет simNumber, а договоры почти без названия. Номер договора из таблицы скрыт. Чтобы понять основание расхода, приходится открывать строки по очереди.

Источник: `src/pages/Expenses.tsx:502`.

**Решение:** выводить номер договора как обязательный fallback, категорию услуги отдельно и ссылку на исходный счёт. Внутри карточки показывать основание и связанные документы.

### 21. Глобальный поиск ведёт в отфильтрованный список вместо найденной карточки

Источник: `src/components/layout/MainLayout.tsx:48`, `src/lib/searchUtils.ts`.

**Решение:** маршрут карточки по ID, например `/contracts/:id` или `?id=...`. Использовать этот же адрес из списков и связанных сущностей. Тогда карточкой можно поделиться внутри системы и восстановить её после обновления страницы.

В счетах отсутствуют собственные поиск и фильтры по компании, договору, периоду, статусу; общий поиск не ищет счета. В карточке SIM начисления суммируются за все периоды (`src/pages/SimCards.tsx:189`), что не подходит для сравнения с месячным лимитом.

### 22. Несколько интерфейсных элементов обещают несуществующие функции

**По коду и UI.** Настройки профиля, пароля, уведомлений, логирования и лимита не сохраняются. «Сохранить изменения» не имеет обработчика. Индикатор уведомлений статичен. «Внести расходы» на дашборде не имеет действия. Кнопки дополнительного фильтра также без обработчиков. В карточке договора вместо символа валюты отображается `?`.

Источник: `src/pages/Settings.tsx`, `src/pages/Index.tsx:101`, `src/components/layout/MainLayout.tsx:167`, `src/pages/Contracts.tsx:553`.

**Решение:** убрать недействующие обещания либо реализовать минимальные реальные действия. Журнал изменений для финансовых записей действительно нужен, его нельзя заменить включённым декоративным переключателем.

### 23. Узкий экран и клавиатурная навигация не обеспечены

**Визуально подтверждено при 390 × 844.** Sidebar занимает 256 px; контент с постоянным pl-64 оставляет узкую полоску, кнопки и таблицы уходят за экран. Горизонтальный скролл появляется на странице целиком.

Источник: `src/components/layout/Sidebar.tsx:89`, `src/components/layout/MainLayout.tsx:58`.

Кликабельные строки реализованы через onClick у tr без клавиатурного эквивалента; многие кнопки-иконки не имеют доступного имени.

**Решение:** сворачиваемая навигация на узких экранах, адаптивная шапка, локальный scroll таблицы; ссылки/кнопки с названием и фокусом. Это требуется и в узкой боковой панели desktop, не только на телефоне.

## Архитектура: минимальный целевой вариант

Сохранить существующий стек и серверные модули. Не добавлять микросервисы, репозитории поверх Convex, универсальные фабрики форм или новый менеджер состояния.

1. **Документ:** исходный файл, вид, номер, оператор, компания, период, распознанные данные, результат проверки, fingerprint. Счёт и детализация различаются явно.
2. **Договор:** компания, оператор, нормализованный номер, категория услуги, условия, ответственный, статус. Номер может требовать составного ключа по оператору/компании; одна глобальная уникальность строки опасна для коротких номеров вроде «2».
3. **Номер/подключение:** явный договор; для интернета — адрес/объект, для мобильной связи — нормализованный номер и ICCID. Общая сущность подключения нужна только если реально вводится учёт адресов; не делать иерархию классов заранее.
4. **Назначение:** номер/подключение, сотрудник или ответственный, даты действия. Это минимальная история для правильного отнесения прошлых расходов.
5. **Начисление:** документ-основание или ручной источник, contractId, период услуги, суммы в копейках, статус. **Распределение:** строки детализации по номерам/сотрудникам, связанные с начислением. Общий расход учитывает начисления, персональный — распределения.
6. **Серверные операции:** применить документ, назначить/снять номер, перепривязать, аннулировать. Каждая проверяет права и бизнес-инварианты и пишет связанные записи атомарно.
7. **UI:** штатные reactive hooks, единый период, адрес карточки по ID, сохранённые связи между карточками. Пагинацию в первую очередь добавить для расходов/счетов, а не строить отдельную подсистему поиска заранее.

## Безопасная последовательность работ

| Этап | Изменения | Условие завершения |
|---|---|---|
| 0. Защита | Проверить backup и восстановление; авторизация, роли, защита upload, ограничение seed | Анонимный доступ закрыт; существующий пользователь входит и видит свои данные |
| 1. Учёт документов | Идемпотентность, атомарное применение, согласованные перепривязка/аннулирование, серверная валидация | Повтор файла не меняет сумму; сбой не оставляет половину операции; удаление не оставляет ложный документ |
| 2. Модель и миграция | ID-связи, периоды, счёт/распределение, история назначений, ответственные, проверка реквизитов и типов услуг | Старые документы и суммы сохранены, неоднозначные связи вынесены в список проверки |
| 3. UI | Исправить дашборд; ссылки на карточки; связанные счета/расходы; рабочие фильтры; убрать макеты; адаптивная навигация | Компания → договор → документ/расход и сотрудник → номер → расходы доступны без поиска через меню |
| 4. Рост объёма | Пагинация и запросы по периоду; убрать повторные full-collect и ручной polling | Итоги полного периода совпадают с данными при объёме более 5000 строк |

Миграция должна быть добавочной: сначала новые необязательные поля, затем dry-run сопоставления, сохранение неоднозначных случаев, сверка сумм/количества, и только после этого переключение записи. Не пересоздавать БД и не пересидировать production. До переключения сохранить baseline текущих 35 начислений и 37 документов.
